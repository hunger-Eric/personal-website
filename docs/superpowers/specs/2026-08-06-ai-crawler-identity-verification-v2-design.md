# AI 爬虫身份验证 V2 设计

日期：2026-08-06
状态：用户已批准，实施计划已编写
适用项目：`E:\project\personal-website`

## 1. 目标

在现有私有 AI 爬虫后台上增加可解释的身份验证能力，区分：

1. 官方可信；
2. 仅 User-Agent 声明、无法强验证；
3. 声明为已知厂商但明确未通过其官方验证规则的疑似伪装；
4. 无法对应已知厂商的其他自动化流量。

设计允许形成完整的长期路线，但实施必须拆成可独立测试、审查和停止的小阶段。任何阶段都不自动授权提交、推送或部署。

## 2. 当前 V1 基线

当前生产链路已经具备：

- `me.itheheda.online/*` 由 Cloudflare Worker 透明代理到现有 Vercel 站点；
- Worker 根据已知 AI 爬虫 User-Agent、有效 Open GEO HMAC 和通用机器人规则分类；
- D1 按小时、分类、爬虫、规范化路径和状态码聚合，保留 90 天；
- `/admin/crawlers` 使用 Basic Auth；Next.js 通过 HMAC 读取 Worker 私有分析接口；
- 数据不包含 IP、查询参数、完整 User-Agent 或逐条原始日志；
- V1 只能证明请求声明的身份，不能证明其确实来自对应厂商。

V2 必须在不破坏上述链路的前提下增量实现。

## 3. 已确认的产品决策

- 零新增月费，复用现有 Worker、D1、Cron 和私有后台；
- 请求发生时允许使用来源 IP、ASN 和 DNS 结果，但不保存原始 IP；
- 国际 AI 爬虫、中国 AI 爬虫、国际搜索爬虫和中国搜索爬虫分别标记用途；
- 官方证据决定可信等级，社区名录或 User-Agent 名录只能帮助发现候选身份；
- 官方规则每日同步；同步失败时继续使用最近一次有效版本；
- 先运行 7 天影子结果，V1 继续作为正式统计；
- 规划可以完整，但每次只执行一个小阶段。

## 4. V2.1 最小交付范围

V2.1 只完成以下闭环：

1. 强验证 OpenAI 的 `GPTBot`、`OAI-SearchBot` 和 `ChatGPT-User`；
2. 强验证 `PerplexityBot` 和 `Perplexity-User`；
3. 识别 `Bytespider`、`Baiduspider`、Sogou 和 360Spider，但先标为“仅 UA 声明”；
4. 生成四级身份聚合结果；
5. 在现有后台增加四张身份卡片和爬虫表的“身份”列；
6. V2.1 以影子模式运行 7 天，不自动替换 V1。

### V2.1 非目标

- Google、百度双向 DNS 强验证；
- ASN 单独作为强验证依据；
- 完整厂商管理平台；
- 地区、厂商和用途高级筛选；
- 通知、导出或逐条请求日志；
- 新增 KV、队列、外部数据库或付费 Cloudflare 产品；
- 保存原始 IP、IP 哈希或完整 User-Agent；
- 修改 Open GEO Console 生产端。

## 5. 身份模型

V2 输出确定等级，不生成不可解释的百分制分数。

| 等级 | 判定条件 | 展示文案 |
| --- | --- | --- |
| `verified_official` | 候选 UA 与厂商匹配，并通过当前有效的官方 IP、双向 DNS 或 HMAC 规则 | 官方可信 |
| `declared_unverified` | UA 可识别，但厂商没有可用强验证资料，或验证暂时无法完成 | 仅声明身份 |
| `suspected_spoof` | UA 声称为某个有权威验证规则的厂商，但来源明确不符合当前有效规则 | 疑似伪装 |
| `other_automation` | 可判定为自动化请求，但无法对应已知厂商 | 其他自动化 |

### 判定约束

- DNS 超时、官方源故障、规则缺失或规则超过有效期时，不得判为疑似伪装；应降级为 `declared_unverified`。
- ASN 和云服务商名称只可作为说明信息，不能独立产生 `verified_official`。
- 有效 Open GEO HMAC 继续归为签名自测；无效签名不得进入可信自测。
- 一个请求只有一个最终 V2 身份等级，四级计数之和必须等于 V2 自动化请求总数。

## 6. 官方证据和厂商规则

V2.1 只将厂商官方发布的数据视为强验证来源：

- OpenAI：V2.1 使用厂商为 `GPTBot`、`OAI-SearchBot` 和 `ChatGPT-User` 分别发布的 IP JSON 数据；不同 UA 必须匹配相应数据源；
- Perplexity：使用官方 `PerplexityBot` 和 `Perplexity-User` IP JSON 数据；
- Open GEO：使用现有 HMAC-SHA256 验证；
- Anthropic：官方当前不提供固定 IP 范围，因此 Claude 系列只能标为“仅声明身份”；
- 中国厂商：V2.1 先扩充 UA 识别。没有官方、稳定、可自动验证的证据时，不得标为“官方可信”。

官方来源必须通过 HTTPS 获取，并经过固定来源、状态码、响应大小、JSON 结构、CIDR 格式和空结果校验。第三方或社区数据可用于发现新的 UA 候选，但不能进入强验证规则。

## 7. 架构与数据流

1. Worker 先按现有方式取得官网源响应；观察失败不得修改官网响应。
2. 仅当 User-Agent 命中已知候选或通用机器人规则时，才进入 V2 分类。
3. V2 验证器在内存中使用来源 IP 和当前规则，输出厂商、用途、可信等级和验证方法。
4. V1 聚合写入保持不变；V2 写入独立影子聚合表。
5. 现有 Cron 增加规则同步步骤，并保留现有清理职责。
6. 私有读取接口在现有 HMAC 合同上增加 V2 预览数据；浏览器不接触来源 IP、规则正文或读取密钥。

V2.1 不引入实时 DNS 查询。需要双向 DNS 的 Google、百度验证在后续独立阶段实现，避免第一版同时引入请求网络调用、缓存和超时策略。

## 8. 数据与隐私

V2 影子聚合记录只包含：

- 小时时间桶；
- 厂商、爬虫、地区和用途标识；
- 可信等级和验证方法；
- 规范化路径；
- HTTP 状态码；
- 请求计数。

规则状态只记录：

- 官方来源标识；
- 内容哈希或规则版本；
- 最近尝试、最近成功和最近有效时间；
- 是否正在使用最近有效版本；
- 脱敏失败代码。

禁止写入 D1、应用日志和后台响应的内容包括原始 IP、IP 哈希、完整 User-Agent、查询参数、官方规则原文和响应正文。

## 9. 规则同步和降级

- 每日 Cron 顺序获取 V2.1 官方数据源；每个来源独立成功或失败。
- 新规则必须完整通过校验后才能替换该来源的旧版本。
- 一个来源失败不得清空其他来源或整个规则集。
- 最近有效规则在最后一次成功同步后的 7 天内继续使用，并在后台标记为“使用最近有效版本”。超过 7 天后，该来源视为没有有效规则。
- 没有有效规则时，对应厂商只能产生 `declared_unverified`，不得产生 `verified_official` 或 `suspected_spoof`。
- 同步错误只记录固定错误码，不记录远端响应正文。

## 10. 最小后台变化

影子模式只增加：

- “V2 身份验证预览”提示；
- 官方可信、仅声明身份、疑似伪装、其他自动化四张卡片；
- 现有爬虫表中的“身份”列；
- 简短的验证方法和规则最近更新时间；
- 规则同步失败或使用旧版本时的非阻塞状态说明。

V2.1 不增加复杂筛选、抽屉、逐条证据视图或新导航层级。移动端继续采用单列卡片和表格容器内横向滚动，不允许页面整体横向溢出。

## 11. 7 天影子运行

影子期内：

- V1 继续作为正式统计和默认页面语义；
- V2.1 只作为预览，不修改历史 V1 数据；
- 不用 V2 结果自动放行、阻止或挑战任何请求；
- 不因验证结果修改 robots.txt、WAF 或 Bot 设置；
- 7 天结束后由用户明确决定继续观察、修复或晋升。

晋升前必须满足：

- 四级身份之和与 V2 自动化请求总数一致；
- V1 已识别请求在 V2 中有对应结果，不存在未解释的系统性缺口；
- 规则缺失和同步失败时没有错误可信或错误伪装结论；
- 官网公开路径、后台鉴权和 Worker 私有接口没有回归；
- 桌面与移动端预览可读；
- 生产观察期没有因 V2 引入新的 5xx 或源站行为变化。

## 12. 小步执行路线

每个阶段单独实现、测试和审查；后续阶段不会因为列入路线而自动执行。

| 阶段 | 单一交付 | 完成证据 |
| --- | --- | --- |
| 0 | 冻结 V1 基线 | 当前数据合同、D1 结构和生产行为已核对 |
| 1 | 定义 V2 类型和纯函数合同 | 四级身份、验证方法和不变量离线测试通过 |
| 2 | 实现规则获取、校验和最近有效版本逻辑 | 成功、损坏、空响应、超时和部分失败测试通过 |
| 3 | 增加 OpenAI 适配器 | 官方范围命中、明确不命中和无有效规则测试通过 |
| 4 | 增加 Perplexity 适配器 | 两种 Perplexity UA 与数据源相互隔离 |
| 5 | 增加四类中国爬虫 UA | 全部为声明身份，不产生虚假强验证 |
| 6 | 增加 V2 影子聚合和最小后台预览 | V1 不变，V2 合计不变量和响应 schema 通过 |
| 7 | 经独立授权部署影子模式 | 生产公开路径、鉴权、接口和移动端只读 QA 通过 |
| 8 | 观察 7 天并形成晋升决定 | 用户审阅真实数据后明确批准或拒绝晋升 |

提交、推送、Cloudflare 资源变更、Vercel 变量变更和生产部署均是独立授权门槛。

## 13. 测试和验收

离线测试至少覆盖：

- IPv4、IPv6 和 CIDR 边界；
- UA 与厂商数据源错配；
- 官方命中、明确不命中、无规则和规则过期；
- 单一数据源失败不污染其他来源；
- 最近有效版本替换的原子性；
- 禁止把 IP、完整 UA 或远端正文写入 D1、日志和 API；
- V1 与 V2 并行写入时，V1 输出保持兼容；
- V2 四级计数不变量；
- Basic Auth、HMAC、`no-store`、无 CORS 和错误状态合同。

生产验证必须经过真实官网入口，但只在单独授权部署后执行。HTTP 200、单元测试或构建通过不能单独证明生产功能可用。
