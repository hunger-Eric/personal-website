## 直接答案

你在聊天框输入一句话，几秒后看到一段流畅的回答。这段时间里，系统通常先把当前问题、必要的对话历史和应用给出的指令整理成模型输入；分词器把它转换为 token；模型处理这些 token 的上下文关系，给出下一个 token 的候选分数；解码程序选出一个，再重复，直到回答结束。若产品启用了搜索或工具，中途还可能插入一次外部调用。这里的“通常”很重要：这是公开论文与实现文档能够支持的文本模型工作图，不是任何一家闭源产品的内部流程图。

用一个问题作线索：“为什么两份报价看起来一样，仍要人工复核？请用两句话回答。”模型可以生成一段有用的解释，但那段话到底依据了什么，取决于它在这次请求中实际收到了哪些材料。语言连贯和事实核对，是两件事。

## 你输入的，未必是模型收到的全部文字

聊天界面把提问显示为一条消息。送进模型前，应用还可能附上角色标记、系统说明、历史对话、检索材料或工具返回值。开源模型的聊天模板就是可核对的例子：它把带 `role` 和 `content` 的消息整理成一条模型可继续生成的序列；不同模型用的模板也不一样。[Hugging Face 聊天模板文档](https://huggingface.co/docs/transformers/main/chat_templating)

这也解释了为什么同一句问题放在两个产品里，未必是在做同一次实验。一个产品可能带着前文，另一个可能提供了搜索结果；有的应用还会限制回答格式。这些差异发生在模型开始生成文字之前。至于某个商业助手具体拼接了什么，只有产品公开说明或可观察的记录才能支持判断，不能从最终文风反推。

## 从文字到上下文表示

分词器把输入拆成 token 并映射为编号。token 不是固定的“一个字”或“一个词”：同一句中文在不同分词器下，可能变成不同数量的 token。[Hugging Face 分词器文档](https://huggingface.co/docs/transformers/main/tokenizer_summary)说明了几种常见方法。模型再把编号映射为可计算的向量，并结合位置信息处理词序。

以常见的自回归 Transformer 文本模型为例，注意力机制让当前位置根据自身及此前位置的表示计算新的表示。为了预测下一个 token，因果遮罩会阻止一个位置偷看它后面的 token。[Transformer 原始论文](https://arxiv.org/abs/1706.03762)提出了注意力架构；[Hugging Face 的缓存解释](https://huggingface.co/docs/transformers/main/cache_explanation)展示了因果注意力在生成时怎样工作。原始 Transformer 是编码器与解码器架构，不能把它的每个实现细节原封不动套给今天的所有聊天模型。

这里很容易把“注意力”听成“模型知道什么重要”。它其实是网络内部对表示进行加权计算的机制。即使模型把“报价”和“人工复核”联系起来，也不等于它检查过这两份真实报价，或已经知道哪一项数字有误。

## 为什么回答是一小段一小段出现的

系统可以先处理整段已有输入，这一步常称为 *prefill*。随后模型在当前上下文后面计算下一个 token 的分数；解码程序依据设定选择一个 token，把它接回序列，再计算下一个。这段逐步生成叫 *decode*。GPT-3 论文把其模型明确描述为自回归语言模型；[Hugging Face 的生成文档](https://huggingface.co/docs/transformers/main_classes/text_generation)则给出了贪心选择、采样、`temperature` 和 `top_p` 等具体解码方式。[GPT-3 论文](https://arxiv.org/abs/2005.14165)

因此，屏幕上的一段完整回答，并非模型先从某个隐藏的“标准答案库”取出全文。模型先给候选 token 分数，经过归一化及解码设置，形成用于选择的条件分布；它可以每步选分数最高的 token，也可以采样。设置和运行条件不同，文字可能变化。这个分布回答的是“当前上下文后面怎样续写”，不能直接当作“这句话有多大概率为真”。

生成时还常用 *KV cache*：保存已处理位置在注意力层中的部分计算结果，下一步继续使用，免得每生成一个 token 都从头计算全部前文。[缓存文档](https://huggingface.co/docs/transformers/main/cache_explanation)说明了这种优化。它帮助加快推理，不是一座会自行更新的知识库。回答也不是无限延长；结束标记、长度上限等停止条件由模型和服务的生成设置决定。

## 逐 token 生成，为什么还能做多步推理

“预测下一个 token”只描述输出接口，不表示模型每次只看最后一个字。每一步的分数都依赖当前可见的整个上下文，以及训练所得的参数；前面已经写出的中间步骤，也会成为后续生成的输入。链式思维提示研究发现，在所测试的算术、常识和符号任务中，让模型写出中间步骤可以改善表现。[链式思维原始论文](https://arxiv.org/abs/2201.11903)

但研究结果不能证明所有商业助手都会展示或采用同样的中间过程。即使一段推理看起来有条理，仍需要检查前提、计算和结论。把“写出了步骤”当作“已经验证”，会把生成过程误认成校验过程。

## 搜索是插进来的另一段流程

如果刚才的问题是“今天这家公司最新的报价规则是什么”，只靠模型参数里已有的模式显然不够可靠。支持检索的应用可以先找资料，把相关段落放进上下文，再让模型回答。检索增强生成（RAG）的原始论文明确区分模型参数中的知识与外部可检索材料。[RAG 论文](https://arxiv.org/abs/2005.11401) 这是一种可选架构，不是每次提问都会自动联网。

工具调用也是如此。模型可以产生一个“请求调用工具”的输出，应用执行搜索、数据库查询或计算，再把结果送回模型，接着生成面向用户的答复。[Hugging Face 的工具模板说明](https://huggingface.co/docs/transformers/main/chat_template_tools_and_documents)给出了可操作的例子。工具做了什么、返回了什么，与模型如何复述结果，应分别检查。产品展示的来源链接，也不自动证明链接支持旁边的每一句话。ALCE 的引用评估研究专门把回答正确性和引用支持程度分开测量。[ALCE 论文](https://arxiv.org/abs/2305.14627)

## 回答前的训练，和这一次回答，不是同一步

逐 token 预测也用于许多文本模型的预训练；训练时会调整参数，让模型从大量文本中学到统计规律。用户这次提问通常是在使用已有参数进行推理，并非重新训练它。GPT-3 论文也展示了在不更新参数的情况下，靠输入中的示例完成任务。[GPT-3 论文](https://arxiv.org/abs/2005.14165)

聊天助手之所以更愿意按指令回答，往往还与后训练有关。InstructGPT 研究用示范答案和人工偏好改进指令遵循，但论文同时指出模型仍会犯简单错误。[InstructGPT 论文](https://arxiv.org/abs/2203.02155)这是一个公开研究实例，不能据此断言所有产品都使用相同训练配方，更不能把“愿意回答”当成“答案已经核实”。

## 适用边界

以上重点解释文本、自回归模型的一条常见路径。不同模型可能采用不同分词器、位置处理、解码与缓存方案；多模态输入还需要额外的图像或音频处理。上下文窗口也有限，而且放得进去不表示都能稳定用好；[《Lost in the Middle》](https://arxiv.org/abs/2307.03172)在所测任务中发现，材料所处位置会影响长上下文问答表现。这个研究结果不能当作所有新模型或商业产品的固定规律。

## 实施步骤

如果要用模型回答一项实际业务问题，先写清问题、允许使用的资料、所需时间范围和答案格式。再确认产品这次有没有搜索、查库或使用附件；如果没有，就不要把回答描述为“查过最新材料”。最后，把需要核对的数字、条件与结论逐条对回原始材料。这个顺序比单纯要求“请准确回答”更可执行。

拿前面的报价问题来说，模型可以帮助列出复核角度；真正判断两份报价是否相同，还需要两份报价原件、版本、税率、交付条件和负责人的确认。它输出了什么，与人最终批准了什么，应留下不同记录。企业流程如何划定这些边界，可参考本站的[服务说明](/services)与[项目页](/projects)。

## 验收清单

留存原问题、模型版本或产品名称、回答时间，以及当次提供的附件、搜索结果和工具记录。抽取回答中的关键事实句，逐句问：它有来源吗？来源真的支持这句话吗？缺少前提或过期了吗？如果应用只能给出一段流畅文本，至少把它当作待核对的草稿。引用评估研究已经说明，“带链接”与“得到完整支持”之间还有距离。[ALCE 论文](https://arxiv.org/abs/2305.14627)
